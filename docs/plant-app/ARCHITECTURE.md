# Архитектура «Подоконника»

«Подоконник» — сайт для тех, кто держит комнатные растения: коллекция с графиком ухода,
база знаний, сообщество садоводов, барахолка, магазины и распознавание по фото.
Работает в браузере на телефоне и компьютере и ставится на главный экран как PWA.

Связанные документы:

- [DATA_MODEL.md](DATA_MODEL.md) — схема базы данных и политики доступа;
- [API.md](API.md) — какие таблицы, RPC и Edge Functions вызывает сайт;
- [FEATURES.md](FEATURES.md) — что умеет приложение и что можно добавить;
- [DESIGN.md](DESIGN.md) — принципы интерфейса.

## 1. Решения и причины

| Требование | Решение | Почему |
|---|---|---|
| Работать на любом устройстве без магазинов приложений | Статический сайт (Next.js `output: "export"`) + PWA | Один код, бесплатный хостинг (GitHub Pages), установка на экран «Домой» |
| Данные пользователей, соцграф, права доступа | Supabase: Postgres + Row Level Security | Правила доступа живут в базе рядом с данными, а не в каждом клиенте |
| Логика, которую нельзя доверить браузеру | Триггеры и RPC в Postgres, Edge Functions (Deno) | Пересчёт графика, квоты, проверка магазинов — там, где их нельзя обойти |
| Секреты внешних сервисов (Pl@ntNet, Gemini, VAPID) | Supabase Vault, чтение только из Edge Functions | Ключ не попадает в браузер и в репозиторий |
| База знаний должна находиться поисковиками | Страницы видов собираются заранее из снимка `species.json` | SEO и мгновенная загрузка без запросов к базе |
| Попробовать без регистрации | Демо-режим: тот же интерфейс репозиториев поверх `localStorage` | Экраны не знают, откуда данные; e2e-тесты не требуют сервера |

## 2. Общая схема

```
┌──────────────────────────────── Браузер (web/) ────────────────────────────────┐
│  app/            страницы (App Router): маршруты и компоновка                  │
│    │                                                                           │
│  components/     экраны по разделам + UI-кит (components/ui)                   │
│    │                                                                           │
│  lib/queries.ts  хуки TanStack Query: кэш, загрузка, сброс кэша после изменения│
│    │                                                                           │
│  lib/data/       контракты репозиториев (repositories.ts)                      │
│    ├── supabase/ реализация на Supabase ───────────────┐                       │
│    └── demo/     реализация в браузере (localStorage)  │                       │
│                                                        │                       │
│  lib/domain/     чистая логика без React и сети:       │                       │
│                  интервалы ухода, достижения, прайс,   │                       │
│                  диагностика, модели и разбор строк    │                       │
└────────────────────────────────────────────────────────┼───────────────────────┘
                                                         │ HTTPS (PostgREST, Storage,
                                                         │ Realtime, Functions)
┌────────────────────────────────── Supabase (supabase/) ▼───────────────────────┐
│ Postgres + RLS          таблицы, триггеры пересчёта графика, RPC               │
│ Storage                 фото растений, записей, объявлений (подписанные ссылки)│
│ Auth                    email и пароль, подтверждение по ссылке из письма      │
│  Edge Functions (Deno)                                                         │
│   identify-plant  вид и болезни по фото: Pl@ntNet + Google Gemini              │
│   news-ingest     сбор новостей из RSS/Atom (pg_cron, раз в час)               │
│   news-reader     статья в «режиме чтения»                                     │
│   push            Web Push: VAPID-ключ и рассылка очереди (pg_cron, раз в мин.)│
│ Vault                   ключи внешних сервисов и секреты cron                  │
└────────────────────────────────────────────────────────────────────────────────┘
```

### Направление зависимостей

`app → components → lib/queries → lib/data → lib/domain`. Нижний слой не знает о верхнем:

- `lib/domain` — чистые функции и типы. Их легко тестировать, и их не нужно менять при
  переходе на другой бэкенд.
- `lib/data` зависит только от `lib/domain` и контрактов. Экраны получают `Backend` через
  `useBackend()` и не импортируют Supabase напрямую.
- Компоненты не ходят в сеть сами: данные берут через хуки из `lib/queries.ts`.

## 3. Сайт (`web/`)

### 3.1 Структура

```
web/src/
  app/                    маршруты; страница только собирает компоненты своего раздела
    (app)/                разделы для вошедшего пользователя и демо (общий каркас AppShell)
    login/, page.tsx      вход и главная для гостя
  components/
    ui/                   UI-кит: кнопки, поля, листы, кольца, тосты, иконки ухода
    plant-card/           карточка растения: фото, факты, уход, график, журнал, место
    new-plant/            форма «Новое растение»: вид, распознавание, место, полив
    feed/                 записи дневников, вопросы, ответы, комментарии
    shop-manage/          кабинет магазина: анкета, статус, загрузка и правка каталога
    *.tsx                 остальные разделы: люди, барахолка, магазины, новости, камера…
  lib/
    domain/               предметная логика (см. 3.2)
    data/
      repositories.ts     контракты: GardenRepository, SocialRepository, ShopRepository…
      supabase/           по файлу на репозиторий + shared.ts (строки, бакеты, id видов)
      demo/               то же в браузере: state.ts, fixtures.ts, seed.ts и репозитории
      schedules.ts        стартовый график ухода — общий для обеих реализаций
    queries.ts            хуки данных
    knowledge.ts          база знаний из снимка: виды, грунты, поиск
    time.ts, format.ts    даты и форматирование
    image.ts, files.ts    сжатие фото, чтение прайса (CSV, .xlsx)
    push.ts, translate.ts Web Push и встроенный переводчик браузера
  data/                   снимки species.json и soil-mixes.json
```

### 3.2 Предметная логика (`lib/domain`)

| Модуль | Что внутри |
|---|---|
| `care.ts` | Виды ухода, свет, горшки. `effectiveIntervalDays` — интервал с поправками на сезон, горшок, свет и привычки хозяина. Та же формула работает в SQL (`*_care_logic.sql`), тесты сверяют результаты |
| `plant.ts` | Растение, видимость, статус полива |
| `species.ts`, `soil.ts` | Вид из базы знаний, поиск по названиям, грунтовые смеси |
| `gamification.ts` | Достижения, опыт и уровни садовода по статистике из `my_garden_stats` |
| `diagnosis.ts` | Справочник симптомов и причин, коды EPPO, разбор ответов Pl@ntNet и Gemini |
| `identification.ts` | Сопоставление ответа распознавателя с видами базы знаний |
| `social.ts`, `people.ts`, `market.ts` | Сообщество, профили, барахолка и переписка |
| `shop.ts`, `price-list.ts` | Магазин и анкета; разбор файла прайса, угадывание колонок, выгрузка |

### 3.3 Данные и кэш

- Каждый раздел — отдельный репозиторий с интерфейсом в `repositories.ts`. `supabaseBackend`
  и `demoBackend` собирают из них объект `Backend`. `session.tsx` выбирает реализацию: есть
  сессия Supabase — живые данные, иначе демо.
- В Postgres у видов uuid, а на сайте slug. Их переводит `SpeciesIds` (`supabase/shared.ts`),
  справочник загружается один раз на сессию.
- TanStack Query кэширует запросы. Ключ начинается с раздела (`plants`, `feed`, `shops`…),
  и после изменения сбрасываются только затронутые разделы.
- Демо-режим повторяет серверные триггеры: пересчёт графика после отметки, отмену отметки и
  «растение в воде». Поэтому сценарии e2e одинаковы для обоих режимов.

### 3.4 Рендеринг и хостинг

- Страницы видов `/plants/<slug>/` генерируются при сборке. Личные экраны рендерятся в браузере
  после входа; параметры передаются в query-строке (`/garden/plant/?id=`), потому что
  статический экспорт не поддерживает динамические сегменты для пользовательских данных.
- `scripts/sync-species.mjs` перед сборкой обновляет снимок базы знаний из Supabase. Без
  переменных окружения используется сохранённый снимок.
- `.github/workflows/web-deploy.yml` публикует `out/` на GitHub Pages при изменениях в `main`.

## 4. Сервер (`supabase/`)

### 4.1 База данных

- Схема, политики, триггеры и RPC — в `supabase/migrations`, по одной миграции на изменение.
  Применённую миграцию не правят: исправление — это новая миграция.
- RLS включена на всех таблицах. Своё можно читать и менять. Чужое видно, только если
  `visibility = 'public'` или `'followers'` при наличии подписки. Блокировка скрывает всё.
- Служебные таблицы (квоты, очередь push, журналы уведомлений) лежат в схеме `private` и из
  браузера недоступны.
- Пересчёт графика — триггер на `care_events`: отметка сдвигает `next_due_at` и подстраивает
  личный коэффициент, удаление отметки возвращает прежние значения.

### 4.2 Фоновые задачи (pg_cron)

| Задача | Расписание | Что делает |
|---|---|---|
| `news-ingest-hourly` | раз в час | Вызывает `news-ingest`: RSS/Atom из `news_sources` → `ingest_news` (дедупликация, привязка к видам) |
| `push-care-reminders` | каждые 5 минут | Кладёт в очередь напоминания об уходе, наступившие по часовому поясу пользователя |
| `push-send-minutely` | раз в минуту | Вызывает `push`, если в очереди есть неотправленные уведомления |

Вызовы из cron подписываются секретами из Vault (`x-cron-secret`).

### 4.3 Распознавание и диагностика

`identify-plant` принимает сжатое фото (JPEG до 1280 px) от вошедшего пользователя:

- `mode: "species"` — Pl@ntNet возвращает кандидатов, сайт сопоставляет их с базой знаний;
- `mode: "diseases"` — Pl@ntNet (коды EPPO) и Google Gemini работают параллельно. Gemini
  выбирает причины из того же справочника, что и сайт (`diagnosis.ts`), поэтому шаги лечения
  одинаковые. Если основная модель перегружена или ответила не по схеме, функция повторяет
  запрос к запасной модели. Если один сервис не ответил, возвращается результат другого.
- Квоты: 20 распознаваний в день на пользователя и 450 на проект (`private.identify_usage`).

### 4.4 Безопасность

- В браузер попадает только publishable-ключ: доступ ограничивают RLS-политики.
- Ключи Pl@ntNet и Gemini хранятся в Vault. RPC `get_plantnet_key` и `get_gemini_key`
  выполняются только от имени `service_role`.
- Фото растений снимаются камерой на сайте: поля выбора файла нет. Перед загрузкой фото
  пережимается в JPEG, при этом EXIF (и геометка) не сохраняется.
- Лимиты на объявления, чаты и сообщения проверяет база, а не клиент.

## 5. Качество

| Проверка | Команда | Что ловит |
|---|---|---|
| Форматирование | `npm run format:check` | Prettier, порядок классов Tailwind |
| Линтер | `npm run lint` | ESLint: правила Next.js, строгие сравнения, порядок и вид импортов, без `console` |
| Мёртвый код | `npm run knip` | Неиспользуемые файлы, экспорты и зависимости |
| Типы | `npm run typecheck` | TypeScript `strict` + `noUnused*`, `noImplicitReturns` |
| Логика | `npm test` | vitest: интервалы, достижения, прайс, диагностика, демо-бэкенд |
| Сценарии | `npm run e2e` | Playwright на телефоне и компьютере в демо-режиме |
| База | `scripts/check-migrations.sh` | Все миграции на чистом Postgres + `supabase/tests/smoke_test.sql` |
| Функции | `node --test …`, `deno test …` | Разбор RSS, ответов Pl@ntNet и Gemini, извлечение статьи |

Все проверки запускает `.github/workflows/plant-app.yml` на каждый PR.
