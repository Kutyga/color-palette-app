# Архитектура приложения «Мой сад» (рабочее название)

Мобильное приложение для iOS и Android: личная коллекция растений, трекинг полива и ухода,
социальная лента с чужими коллекциями и база знаний по растениям с рекомендациями по уходу.

Связанные документы:

- [DATA_MODEL.md](DATA_MODEL.md) — схема базы данных
- [API.md](API.md) — контракты API и событий
- [FEATURES.md](FEATURES.md) — функциональность, дополнительные идеи и дорожная карта

---

## 1. Цели и ограничения

| Требование | Решение |
|---|---|
| Одна кодовая база для iOS и Android | Flutter (Dart) |
| Напоминания о поливе должны работать без интернета | Offline-first: локальная БД + локальные уведомления, синхронизация в фоне |
| Социальная часть (профили, подписки, лайки, комментарии) | Серверная БД с Row Level Security, лента на сервере |
| База знаний по тысячам видов с поиском | Postgres full-text + trigram, кэш на клиенте |
| Распознавание растения по фото | Внешний API (Plant.id / PlantNet) через серверную функцию, ключи не попадают в клиент |
| Быстрый старт небольшой командой | BaaS на старте (Supabase), возможность вынести логику в отдельный сервис позже |

## 2. Общая схема

```
┌────────────────────────────── Мобильный клиент (Flutter) ──────────────────────────────┐
│  UI (виджеты, экраны)                                                                   │
│     │                                                                                   │
│  Presentation: Riverpod-провайдеры / контроллеры состояний                              │
│     │                                                                                   │
│  Domain: сущности, use-cases (AddPlant, LogWatering, CalculateNextWatering, ...)        │
│     │                                                                                   │
│  Data: репозитории ──┬── Local DB (Drift/SQLite) ── очередь исходящих изменений (outbox) │
│                      └── Remote (Supabase SDK / REST)                                   │
│  Сервисы: локальные уведомления, камера, геолокация (для климата), аналитика, крэши      │
└─────────────────────────────────────────┬───────────────────────────────────────────────┘
                                          │ HTTPS / WebSocket (Realtime)
┌─────────────────────────────────────────▼───────────────────────────────────────────────┐
│                                   Backend (Supabase)                                    │
│  Auth (email, Apple, Google)   PostgREST API   Realtime   Storage (фото)                 │
│  Postgres + RLS: пользователи, растения, события ухода, соцграф, база знаний             │
│  Edge Functions (TypeScript/Deno):                                                      │
│    • identify-plant   — проксирует фото в Plant.id, сопоставляет с видом из базы знаний  │
│    • care-scheduler   — cron: пересчёт графиков, push о пропущенном поливе               │
│    • feed-fanout      — формирование ленты подписок                                      │
│    • weather-adjust   — корректировка интервалов по погоде/сезону                        │
│    • moderation       — проверка фото/текстов (NSFW, спам)                               │
└──────────────┬──────────────────────────────┬─────────────────────────────┬─────────────┘
               │                              │                             │
        FCM / APNs (push)          Plant.id / PlantNet API        Open-Meteo (погода)
               │
        CDN для изображений (Supabase Storage + image transformations)
```

### Почему так

- **Flutter** — один код, нативная производительность, хорошая поддержка камеры, уведомлений, SQLite.
  Альтернатива: React Native (если в команде сильный JS/TS) или Kotlin Multiplatform (если нужен
  максимально нативный UI). Для MVP Flutter даёт лучший баланс скорости и качества.
- **Supabase** — Postgres (реляционные данные соцграфа и базы знаний ложатся естественно),
  встроенные Auth, Storage, Realtime, RLS. Нет vendor lock-in: это обычный Postgres, миграции
  переносятся на собственный сервер.
- **Offline-first** — полив происходит дома, часто без внимания к сети; уведомления нельзя
  ставить в зависимость от сервера.

## 3. Клиент (Flutter)

### 3.1 Структура проекта (feature-first + чистая архитектура)

```
lib/
  app/                      # точка входа, роутинг (go_router), темы, DI
  core/
    db/                     # Drift: таблицы, DAO, миграции
    sync/                   # SyncEngine, outbox, разрешение конфликтов
    network/                # Supabase client, интерсепторы, ретраи
    notifications/          # flutter_local_notifications + FCM
    media/                  # съёмка, сжатие, загрузка фото
    l10n/                   # локализация (ru, en, ...)
    utils/
  features/
    auth/                   # вход, регистрация, онбординг
    collection/             # мои растения, «комнаты»/локации, карточка растения
    care/                   # полив, удобрение, пересадка, опрыскивание; журнал; график
    reminders/              # расчёт и планирование уведомлений
    knowledge_base/         # каталог видов, поиск, статьи, рекомендации
    identify/               # распознавание по фото
    social/                 # лента, профили, подписки, лайки, комментарии
    diagnostics/            # «что с моим растением?» — симптомы и болезни
    profile/                # настройки, приватность, экспорт данных
  shared/                   # общие виджеты, дизайн-система
```

Каждая фича содержит `data/` (репозитории, DTO), `domain/` (сущности, use-cases) и
`presentation/` (экраны, провайдеры).

### 3.3 Offline-first и синхронизация

1. Все изменения пользователя (добавил растение, отметил полив) пишутся **сначала в локальную БД**
   и в таблицу `outbox`. UI обновляется сразу.
2. `SyncEngine` при наличии сети отправляет записи из `outbox` батчами (идемпотентно — у каждой
   записи клиентский UUID).
3. Pull: запрос изменений с сервера по `updated_at > last_sync_at` для собственных сущностей;
   чужой контент (лента, база знаний) — обычный кэш с TTL.
4. Конфликты: для собственных данных — *last-write-wins* по `updated_at`; события ухода
   (`care_events`) — только добавление (append-only), поэтому не конфликтуют.
5. Удаления — мягкие (`deleted_at`), чтобы синхронизировать их на другие устройства.

### 3.4 Напоминания о поливе

- Расчёт следующей даты — чистая функция в domain-слое (одинаковая логика на клиенте и в
  серверной функции):

  ```
  next_due = last_watered_at + base_interval
             × season_factor(месяц, полушарие)
             × pot_factor(материал, размер)
             × light_factor(освещённость места)
             × user_adjustment        // обучается: если пользователь систематически
                                      // поливает раньше/позже, интервал подстраивается
  ```

- `base_interval` берётся из базы знаний (вид) или задаётся вручную.
- Клиент планирует **локальные уведомления** на ближайшие N событий; группирует их («Сегодня
  полить 4 растения») в выбранное пользователем время.
- Сервер (`care-scheduler`, cron раз в час) шлёт push только как резерв: если растение
  просрочено > 1 дня и клиент давно не синхронизировался, либо если растение общее для
  нескольких людей (семья) и полил кто-то другой.

## 4. Backend

### 4.1 Модули

| Модуль | Ответственность |
|---|---|
| Auth | Регистрация, OAuth (Apple обязателен для iOS при наличии других соц-логинов), сессии |
| Collection | Растения пользователя, локации (комнаты/балкон/сад), фото |
| Care | События ухода, расписания, расчёт просрочек |
| Knowledge Base | Виды, семейства, параметры ухода, статьи, болезни и вредители |
| Social | Профили, подписки, лента, лайки, комментарии, жалобы |
| Identification | Интеграция с Plant.id / PlantNet, маппинг на локальный каталог |
| Notifications | Токены устройств, отправка push, настройки тихих часов |
| Moderation | Автопроверка изображений и текстов, очередь ручной модерации |
| Admin/CMS | Редактирование базы знаний (Supabase Studio или простая веб-админка) |

### 4.2 Безопасность и приватность

- Row Level Security на всех таблицах: владелец читает/пишет свои данные; чужие — только если
  `visibility = 'public'` или (`'followers'` и есть подписка).
- Геолокация хранится только на уровне города/климатической зоны, никогда — точные координаты.
- Из EXIF фото удаляется геометка перед загрузкой.
- Ключи внешних API (Plant.id, погода) — только в Edge Functions.
- Rate limiting на распознавание (дорогой внешний вызов) и на создание комментариев.
- Экспорт и удаление аккаунта (GDPR / 152-ФЗ, требование App Store).

### 4.3 Хранилище фото

- Бакеты: `plant-photos` (приватные/публичные по политике растения), `kb-images` (публичные).
- Клиент сжимает фото до ~1600px, WebP/JPEG 80%.
- Превью генерируются через image transformations Supabase (или imgproxy) и отдаются через CDN.

### 4.4 Лента

- MVP: *fan-out on read* — запрос последних публичных постов/событий тех, на кого подписан
  пользователь, с курсорной пагинацией (`created_at, id`). Достаточно до ~100k пользователей.
- Масштабирование: *fan-out on write* в таблицу `feed_items` через `feed-fanout`, для
  «звёздных» аккаунтов — гибрид.
- Вкладка «Интересное» — популярное за неделю (лайки с затуханием по времени) + по видам,
  которые есть у пользователя.

## 5. База знаний

- Источник данных: открытые датасеты (GBIF для таксономии, Wikipedia/Wikidata для описаний) +
  собственная редакторская разметка параметров ухода. Лицензии проверяются для каждого источника.
- Каждый вид имеет структурированные параметры ухода (свет, полив, влажность, температура,
  почва, удобрение, пересадка, токсичность для животных/детей, сложность) — см. DATA_MODEL.md.
- Поиск: `pg_trgm` + `tsvector` по русским и латинским названиям и синонимам.
- Клиент кэширует просмотренные карточки и «топ-500» популярных видов для офлайн-доступа.
- Версионирование контента (`kb_version`) — клиент докачивает только изменения.

## 6. Инфраструктура и процессы

| Область | Решение |
|---|---|
| Окружения | `dev` / `staging` / `prod` — отдельные проекты Supabase |
| Миграции БД | `supabase/migrations` в репозитории, применяются в CI |
| CI/CD | GitHub Actions: `flutter analyze`, тесты, сборка; Fastlane → TestFlight / Google Play Internal |
| Feature flags / удалённая конфигурация | Firebase Remote Config |
| Мониторинг | Sentry (клиент + функции), логи Supabase, алерты на ошибки cron |
| Тесты | unit для domain (расчёт полива, sync), widget-тесты экранов, integration-тесты на эмуляторах |
| Локализация | ARB-файлы, ru + en на старте |

## 7. Масштабирование в будущем

- Вынести тяжёлую логику (лента, рекомендации, модерация) в отдельный сервис (NestJS/Go) рядом с
  тем же Postgres.
- Поиск по базе знаний — Meilisearch/Typesense при росте каталога и требований к опечаткам.
- Собственная ML-модель распознавания (TFLite на устройстве) для снижения затрат на внешний API.
- Очереди (pg-boss / Redis) для push-рассылок и обработки фото.
